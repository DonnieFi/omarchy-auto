# iOS edition — repository topology

This directory is the Xcode-project root for the iOS edition of Omarchy Auto
([ADR-0017](../docs/planning/DECISIONS.md#adr-0017--omarchy-everywhere-on-ios-native-swift-one-repo-three-surfaces)).
The decision record and owner-facing plan live in
[`docs/planning/`](../docs/planning/) — see
[`IOS-ROADMAP.md`](../docs/planning/IOS-ROADMAP.md).

## What belongs where

| Area | Location | Owner toolchain |
| --- | --- | --- |
| Xcode project, Swift sources, WidgetKit extension, CarPlay scene | `ios/` | Xcode (Mac) |
| Android apps | `core/`, `auto/`, `launcher/`, `navigation-spike/` | Gradle (any host) |
| Shared design tokens | [`design/omarchy-themes.json`](../design/omarchy-themes.json) | generated by Gradle, consumed by both |

Gradle stays Android-only and Xcode stays out of Gradle: no shared build
logic, no iOS targets in `settings.gradle.kts`. The two toolchains meet only
through committed artifacts — the tokens file, recorded route fixtures,
artwork and credits — which is the ADR-0017 sharing contract. The Xcode
project itself is created by the shell/widget/spike beads
(`omarchy-h7w.6` / `.3` / `.2`), not by the topology bead.

## Design tokens

`design/omarchy-themes.json` (schema 1) is the deterministic export of the
ten Omarchy palettes from
[`core/src/main/java/com/omarchy/auto/core/Theme.kt`](../core/src/main/java/com/omarchy/auto/core/Theme.kt).
Colors are `#AARRGGBB` strings; `scrimAlpha`/`stageAlpha` are `0–255`.
The export is byte-stable: the same Theme.kt always produces identical
bytes (LF endings, fixed field order, themes in declaration order), so the
iOS side can vendor the file as a bundle resource.

```sh
# Verify the committed file matches Theme.kt (runs in CI on every PR):
./gradlew :core:testDebugUnitTest

# Regenerate after a theme change:
./gradlew exportDesignTokens -Pomarchy.updateDesignTokens=true
```

`:core:testDebugUnitTest` fails if someone edits `Theme.kt` (or the JSON)
without regenerating — the byte-for-byte comparison and an independent
decode-and-compare of every theme id, name, color and alpha both run there
(`DesignTokensTest`).

### Swift decoding contract

[`DesignTokens/Sources/ThemeTokens/ThemeTokens.swift`](DesignTokens/Sources/ThemeTokens/ThemeTokens.swift)
is the dependency-free Foundation decoder for the tokens file, packaged as
the local SwiftPM package [`DesignTokens`](DesignTokens). **CI compiles and
unit-tests it on GitHub's `macos-26` runner (Xcode 26)** in the
[iOS & Shared workflow](../.github/workflows/ios.yml): all ten themes
decode from the committed `design/omarchy-themes.json`, tokyo-night asserts
`background == "#FF1A1B26"` and `scrimAlpha == 89`, every color parses with
full opacity, and bad colors/alphas are rejected. A local Mac is therefore
not required for the tokens surface. The app and widget targets pick the
package up when the Xcode project lands (beads `omarchy-h7w.6` / `.3`);
a local Mac is still needed for interactive app development, per the
[roadmap](../docs/planning/IOS-ROADMAP.md) prerequisites.

## CI routing

- [`android.yml`](../.github/workflows/android.yml) — unchanged: Linux, runs
  on every push/PR, gates the Android build, lint and asset guard.
- [`ios.yml`](../.github/workflows/ios.yml) — "iOS & Shared": the
  shared-input gate for both platforms. It is also the repository's only CI
  execution of the `:core` unit tests. It verifies the committed tokens
  against `Theme.kt` and proves regeneration is a byte-identical no-op diff.
  Cheap, Linux, always reporting so a required check never pends when only
  one platform changes.
- The same workflow's `swift-tokens` job runs the SwiftPM token tests
  (`ios/DesignTokens`) on GitHub's `macos-26` runner — Xcode 26, no local
  Mac needed for the tokens surface.
- The full macOS Xcode app job (build + tests of the Xcode project) joins
  when the Xcode project lands, gated to `ios/**` and shared-input changes
  so the expensive runner is not billed for Android-only work. Keep the
  always-reporting Linux gate when that happens.
